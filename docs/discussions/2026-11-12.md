## 14:10 GitHub Repo 分析：ggml 與 ONNX Runtime

**使用者指令**

> https://github.com/ggml-org/ggml
> https://github.com/microsoft/onnxruntime

**執行方式**

- 先派兩個 librarian 子代理平行分析，**兩者皆逾時無回應**（累計 30 分鐘無活動）。
- 改為自行以 `gh` API 直接查證：repo metadata、release tags、目錄樹、CMakeLists、`include/ggml.h`、README、`docs/gguf.md`。

**產出**

- 完整分析文件：[`docs/analysis/ggml-vs-onnxruntime.md`](../analysis/ggml-vs-onnxruntime.md)
- 內容涵蓋：專案元資料對照、ggml 五大抽象與 17 個後端、量化型別全表、GGUF 格式、ORT 執行管線與 21 個 EP、plugin EP 架構轉向、171 個圖優化器、MLAS、誠實痛點、選型建議、趨勢判讀、可重現查證清單。

**關鍵結論（摘要）**

1. **本質差異**：ggml 是「張量庫（積木）」，ORT 是「模型執行引擎（VM）」。這是所有比較的根源。
2. **量化路線根本不同**：ggml 把量化做進型別系統（每種 quant 綁定專屬 kernel）；ORT 把量化做成工具鏈（產生標準 ONNX 算子）。前者榨效能、後者換通用性。
3. **治理落差最大**：ggml 的核心開發主場其實在 llama.cpp（README 明講 PR 去那邊提，commit 充滿 `sync : llama.cpp`），docs 只有 1 篇；ORT 有 59 篇文件、roadmap、CODEOWNERS、官方多語言 API。
4. **意外發現**：ORT main 分支已在做 **GGUF 權重格式的 CUDA GEMV 最佳化** 與 **MoE expert offload**（2026-11-12 的 commit）。兩者領域邊界正在崩塌。
5. **共同趨勢**：雙方都轉向「後端插件化」（ggml `GGML_BACKEND_DL` ↔ ORT plugin EP），原因是硬體碎片化速度超過編譯期整合的能力。
6. **實務建議**：少量 transformer 架構 + 邊緣推論 → ggml/llama.cpp；多樣模型 + 企業/多平台/NPU → ORT。

**已知限制**：未編譯、未實測 benchmark；效能敘述皆為架構推論。

**新增驗證（原始碼級）**

- `src/ggml-common.h`：以 `static_assert` 公式推導出 14 種量化格式的精確 bits/weight（如 `Q4_0`=4.500、`Q4_K`=4.500、`Q6_K`=6.562、`TQ1_0`=1.688、`MXFP4`=4.250）。
- `src/ggml-backend.cpp`：確認 `ggml_backend_sched_split_graph()`（:1474）與 `ggml_backend_sched_graph_compute()`（:2372）的「一次 dispatch、backend 內迴圈」模型。
- `onnxruntime/core/framework/graph_partitioner.cc`：確認 `GraphPartitioner::Mode`（kNormal / kAssignOnly / kOrtFormatLoad）、`GetCapabilityForEP()` 雙次呼叫機制、`PartitionOnnxFormatModelImpl()`。

**技術論點摘要（六個核心論點）**

1. Decode 是頻寬受限（算術強度 ≈ 2 FLOP/byte），**位元寬線性決定速度上限**；prefill 才是算力受限。
2. ggml 的量化開銷已近理論下限（4-bit → 4.5 bit，僅 12.5% overhead），且**同為 4.5 bit 時 `Q4_0` 通常比 `Q4_K` 快**（scale 解包成本），證明「佈局決定速度」。
3. 同位元寬下三個決勝點：kernel 是否為佈局手寫、有無格式轉換稅、dispatch 開銷。ggml 在「格式=kernel 佈局」綁死上勝出。
4. **契約強度差異**：ggml 量化是硬性契約（不支援就編不過/載不進）；ORT 是軟性契約（EP 不支援 → **靜默 fallback，慢 5–10× 卻不報錯**）。
5. **可最佳化層級錯位**：ORT 在圖層最佳化（171 transformers），但 LLM 的收益在「執行策略」（paged KV cache、speculative decoding、連續 batching），圖層看不見 → 這是 llama.cpp 存在的結構性理由。
6. ORT 的成本結構（長編譯、大二進位、慢冷啟動、有 ABI）是為伺服器設計；ggml（mmap 零載入、無 ABI、幾 MB）是為邊緣設計。

**可證偽預測（已標記為預測，非數據）**：batch=1 CPU decode ggml 勝 1.5–3×；pp512 差距小甚至 ORT 勝；batch≥8 ORT 反超；冷啟動 ggml 大幅勝。若第一項不成立，則 dispatch 開銷推論被否證。

**狀態**：未建立任何測試檔案（`.bench/` 從未建立），無需清理。僅新增/修改 MD 文件。

## 14:40 問題：ggml 可以轉換成 ORT 嗎？

**使用者指令**

> ggml 有可以轉換成ORT嗎?

**查證結果（文件 + 原始碼層級）**

答案是**可以，而且官方支援**，但方向與直覺相反：**不是把 ggml 轉成 ONNX，而是讓 ORT 直接吃 GGUF。**

四條路徑：

1. **路徑 1（建置期）**：`onnxruntime-genai` 的 model builder `-i/--input` 直接接受 `gguf_path`（限 **F16/F32 GGUF**）。內部 `src/python/py/models/loaders/gguf.py` 用 `GGUFReader` 把 GGUF 包裝成「attribute 結構相同的假 HF 模型」，因此既有 HF→ONNX 建圖程式碼無需修改。
2. **路徑 2（執行期，零轉換，最推薦）**：`genai_config.json` 的 `gguf_initializers` 讓 ONNX 圖直接引用 `.gguf` 內的 initializer，`mmap` 直讀、不需 `.onnx.data`、不複製。支援 `share`（多模型共用 device 記憶體）、`data_type`、`shape`（3D 打包張量）。限制：pipelined decoder 與 Moonshine ASR 不支援。
3. **路徑 3（ORT core 層，最深整合）**：`docs/PackedWeightFormats.md` 是正式格式契約，定義 `MatMulPacked` / `GatherPacked` / `MoEPacked`，pin 在 llama.cpp commit `970b51ce`。ORT 明文宣告佈局語意**凍結**，ggml 上游改動不得重新詮釋 ORT 模型。
4. **路徑 4（不推薦）**：GGUF → HF → ONNX。llama.cpp **沒有官方反向轉換器**，只有 `convert_hf_to_gguf.py` 單向；社群 `convert_gguf_to_hf.py` 品質不一。缺點：反量化→再量化二次精度損失、需 2× 磁碟。

**最關鍵的發現（易踩坑）**

`PackedWeightFormats.md` 僅支援 16 個 ggml type ID：F32(0)、F16(1)、Q4_0(2)、Q5_0(6)、Q8_0(8)、Q5_K(13)、Q6_K(14)、IQ2_XXS(16)、IQ2_XS(17)、IQ3_XXS(18)、IQ4_NL(20)、IQ2_S(22)、IQ4_XS(23)、BF16(30)、NVFP4(40)、Q2_0(42)。

→ **`Q4_K`（ID 12）不在清單**。生態最普及的 `Q4_K_M` 反而不能用，須改用 `Q5_K_M`/`Q6_K`/`Q4_0`。
→ 「ORT 支援 GGUF」≠「ORT 支援你手上那個 GGUF」。

**對第 7 節趨勢判讀的修正**

原本推論「邊界模糊」→ 升級為：**ORT 已把 ggml 的量化佈局納入自己的模型格式契約，並刻意凍結語意、拒絕跟隨 ggml 上游變動。這是在吸收 ggml 的成果，同時切斷對 ggml 的依賴——比單純「支援 GGUF」嚴重得多。**

**狀態**：已寫入 [`docs/analysis/ggml-vs-onnxruntime.md`](../analysis/ggml-vs-onnxruntime.md) 新增第 10 章。無測試檔案產生。

## 15:20 — 路徑 2 落地實作（gguf_initializers 規格查證）

**問題**：路徑 2「ORT 直接吃 GGUF 量化權重」在實務上到底怎麼寫？最小 `genai_config.json` 長什麼樣？

**查證來源**：`docs/GGUFInitializers.md`（108 行全文）、`test/cpp/engine/gguf_initializers_tests.cpp`、`docs/NemotronBolt.md`、`src/config.{h,cpp}`、`src/models/model.cpp`、ORT `contrib_ops/cuda/quantization/matmul_packed.*`、`GENAI src/python/py/models/builders/base.py`。

**schema 重點**

- 可掛在 `model.decoder` / `model.draft` / `model.dflash2` / `model.mtp` 四個位置。
- 寫法兩種：外部路徑字串，或 inline 物件（外層另有 `config_file`，但外部映射檔禁止再嵌套）。
- 欄位 7 個：`config_file`、`files`、`share`、`tensors`，以及 `tensors.<name>` 的 `gguf_name`（映射物件必填）、`file`、`data_type`、`shape`、`share`。**未知欄位一律拒絕，拼法唯一。**
- `tensors` 是 **ONNX initializer 名 → GGUF 名** 的映射；短格式寫字串，長格式才需要 `shape`/`data_type`。
- **pipelined decoder 與 Moonshine（`streaming_enc_dec_asr`）明確不支援**，會報錯而非降級。
- 只驗證被映射選到的張量；GGUF 內含不支援型別沒關係，選到才失敗。

**shape 預設公式（最易錯）**

```
區塊量化： [dims[n-1], ..., dims[1], (dims[0]/blck_size)*type_size]
非量化：   [dims[n-1], ..., dims[0]]
```

ONNX 端看到的是「整個 GGUF blob 攤平」。Q4_0（blck 32、type_size 18）的 `[4096,4096]` 權重 → `[4096, 2304]`，位元組數 9,437,184 ✓。K-quant 的 blck 是 256。

**載入行為**

- mmap 唯讀一次 + 依 `st_dev:st_ino` 快取 tensor directory。
- `share:false` → non-owning `OrtValue` + `use_external_initializer_file_buffers_directly=1`；**真正 zero-copy 需 ORT ≥ 1.32.0（PR #33877）**，且僅「>127 bytes、位址對齊元素大小、little-endian」才借用。
- `share:true` → 上傳一次到裝置，`g_shared_initializers` 跨 session 共用；**DML 直接拒絕**。

**最關鍵的發現（推翻上一輪的樂觀程度）**

`gguf_initializers` 只解決「權重怎麼進來」，沒解決「圖怎麼來」。三個硬性前提目前全部缺失：

1. 圖必須以 **`MatMulPacked`** 消費權重（單一 GGUF blob、`UINT8`）——而 `MatMulPacked` **只有 CUDA kernel**（只在 `cuda_contrib_kernels.cc` 註冊）。
2. builder **完全不能**產 packed 圖：`builder.py`/`builders/base.py` grep `MatMulPacked|GatherPacked|MoEPacked` → 0 筆。
3. ORT **沒有** nbits→packed 融合：`core/optimizer/` 只有 `dq_matmulnbits_fusion` 與 `matmul_nbits_*` 系列。

builder 的 int4 產出是 `MatMulNBits` 三分量佈局（`algo_config ∈ default/rtn/k_quant`，`k_quant` 走 Neural Compressor，輸出 `weight_Q4G32` + `weight_scale` + `weight_zp`）；scale 是獨立 initializer，而 `MatMulPacked` 把 scale 放在 block 內（`d` 欄位）——**兩者佈局不相容**。

→ **路徑 2 = 模型發佈方預備好 packed 圖 + 手寫對映 JSON 的專用通道**，唯一公開實例是 Nemotron-3.5-Bolt-74B-A9B-24GB（843 個 target 張量 + 兩份 JSON）。對一般使用者**沒有自助入口**；本機（RTX 4050 6GB、無 nvcc/cmake）**完全不可用**。

**狀態**：已寫入 [`docs/analysis/ggml-vs-onnxruntime.md`](../analysis/ggml-vs-onnxruntime.md) 新增第 12 章（含最小範例、對映表、載入行為、硬性前提、重現指令）。無測試檔案產生。

## 15:35 — 方向決策：ggml 優先，穩定後再轉 ORT

**使用者決策**：「我想以 ggml 為主要研究目標，當 GGML 可用穩定後再轉換成 ORT。」

**評估**：合理，且與技術事實一致。

1. GGUF 與量化格式的源頭在 ggml，先掌握上游。
2. ORT 對 GGUF 的支援是單向吸收（凍結佈局語意、無反向路徑）——先做 ORT 會被綁在下游。
3. 本機建置門檻：llama.cpp 遠低於 ORT GenAI。

**名詞釐清（重要）**：`ggml-org/ggml` 的 examples 只有 `gpt-2`、`gpt-j`、`mnist`、`sam`、`yolo`、`magika`、`simple`——**沒有 llama**。要跑現代 LLM 必須用 `llama.cpp`（vendored ggml）。兩者是同一棧的兩層，不是二選一。

**本機環境實測（WSL2 修正）**

- 平台：`6.18.33.2-microsoft-standard-WSL2`
- GPU：RTX 4050 Laptop, **6141 MiB**, driver 610.91（`nvidia-smi` 正常）
- `cmake`：**未安裝** ← ggml 建置必需
- `nvcc`：未安裝，**但 WSL 內裝 `cuda-toolkit` 不需要 Windows 驅動 → 可裝**
- Vulkan ICD：只有 mesa 的 `nouveau/intel/radeon/lvp`，**缺 dzn 與 nvidia** → Vulkan 後端暫不可用

→ **修正先前判斷**：「無 nvcc → GPU 不可行」不成立。`nvcc` 是套件問題；真正缺的是 `cmake`。

1. **保留 F16 GGUF 為唯一真實來源**，不要從 `Q4_K_M` 反量化再量化（二次損失）。
2. ggml 端可自由用 `Q4_K_M`；只要 F16 在，未來就能走路徑 1（F16 GGUF → builder）產出 ORT 模型，不會被 `Q4_K` 不支援卡死。

**三階段**：P1 CPU 可跑 → P2 CUDA 部分 offload → P3 讀原始碼/寫 example。

## 16:30 — 需求補充：異質混用（不要純 CPU / 純 GPU / 純 NPU）

**使用者要求**：「我要能混用，不要只是純CPU 或純GPU 或純NPU。」

**查證結論：混用有三種完全不同的語意，且 NPU 混不進來。**

| 語意 | 機制 | 平行？ | 用途 |
| --- | --- | --- | --- |
| 時間分層 | `-ngl N`（前 N 層 GPU、其餘 CPU） | 否，序列交接 | 容量 |
| 張量覆寫 | `-ot 'pattern=CPU'`（fit 自動產生） | 否 | 把 MoE experts 釘 CPU |
| 空間分割 | `-sm row` + `-ts` | **是**（多 GPU） | 提速 |
| 張量平行 | `-sm tensor` | 是（實驗性，fit 不支援） | 多 GPU |

**關鍵事實**：`ggml_backend_sched` 依 `supports_op` 切 subgraph、**依序**執行、跨裝置插 copy → **CPU+GPU 混用不會更快**，只解決容量。ggml 沒有 CPU+GPU 協同 kernel。唯一真平行是多 GPU 的 `-sm row`。

**NPU 無法混用（原始碼證據）** — `src/ggml-openvino/ggml-openvino.cpp:1127`：

> "Only the device selected by `GGML_OPENVINO_DEVICE` is offered for offload. The others are registered for discovery (`--list-devices`) only; llama.cpp skips IGPU devices when a GPU exists."

三層限制：
1. 一次只暴露一個 OpenVINO 裝置（env 決定），其餘只供列舉。
2. 選中的回報 `GPU`，其餘回報 `IGPU` → llama.cpp 有 GPU 時跳過 IGPU。
3. NPU 走 **static shape**（README），LLM decode 是動態 shape；且原始碼註解直言「NPU memory is too small even for kvcache」。

→ `-dev CUDA0,NPU0` 目前不存在。NPU 是「整檔切換」層級，不是排程層級。

**可行解：工作分流（行程/服務層）**
- 生成 → llama.cpp + CUDA
- 無狀態任務（embedding / rerank / OCR / VAD）→ NPU（OpenVINO/ORT）
- 超量/備援 → CPU only（永久安全網）
- **不可跨越**：同一生成請求的 prefill 丟 NPU、decode 丟 GPU（KV cache 無法跨引擎交接）

**狀態**：已寫入 [`docs/design/hw-autoconfig.md`](../design/hw-autoconfig.md) 新增 §6.5（三種語意表、混用不加速的推導、NPU 硬限制原文、工作分流架構圖、policy 決策規則 6 條）。
