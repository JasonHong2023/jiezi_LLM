### 發現的問題（依嚴重度排序）

**1. CPU 親和性設定錯了：`taskset -c 0-11` 實際只用到 6 個核心（已實機查證）**

`lscpu -e` 顯示邏輯 CPU 是兩兩一組（0,1→core 0；2,3→core 1……）。所以 `0-11` 只涵蓋 core 0–5，也就是 6 個核心各開 2 條 SMT 執行緒，而不是預算宣稱的「12 個可用實體核」。

- `hetero-llm/facts.json`：`budgets.cpu.affinity_hint = "0-11"`，由 `scripts/hwprobe.py:433` 的 `f"0-{usable_threads - 1}"` 產生，假設了邏輯 CPU 編號等於核心編號。
- 影響：24.1 t/s 的 baseline 是在約一半的 CPU 資源下跑出來的。未來跟它比較的數字都會失真。
- 修法：依 `/sys/devices/system/cpu/cpu*/topology/core_id` 選核心，例如每個核心取一條執行緒（`0,2,4,…,22`），或直接用 `0-23`。
- 更深一層：i7-14700HX 實體是 **8P + 12E = 20 核 / 28 緒**。WSL2 呈現的「14 核 × 2 緒」是虛擬拓撲，vCPU 不固定對應實體核。所以「保留 2 個實體核」在 WSL 內本身就無法精確落實，文件應註明這只是近似值。

**2. 解碼速度預估偏樂觀約 2 倍（推論）**

1.7B Q4_K_M 權重約 1.107 GB，乘 24.1 t/s 等於有效頻寬約 27 GB/s。分析文件 §13.6 假設 CPU 有 60–70 GB/s，推得 8B 為 12–14 tok/s；改用 27 GB/s 推算只有約 5–6 tok/s。這次 baseline 加了 `--no-warmup`，又受問題 1 拖累，所以還不能定論。修好親和性後重跑 `llama-bench` 才能確認。

## 論文分析：LittleBit（arXiv 2506.13771v5）

**使用者指令**

**來源與範圍**：讀了 arXiv HTML 全文，加上 PDF 才有的附錄 G（超參數）、H（推論效率）、I（限制）；另用 `gh` 查了官方 repo `SamsungLabs/LittleBit`。下文的數字凡標「自算」的，都是我依論文公式或表格重新推算的結果，不是論文原文。

### 1. 基本資料

| 項目 | 內容 |
| --- | --- |
| 標題 | LittleBit: Ultra Low-Bit Quantization via Latent Factorization |
| 作者 | Banseok Lee、Dongkyu Kim（共同一作）、Youngcheon You、Youngmin Kim — Samsung Research |
| 發表 | NeurIPS 2025；v1 2025-05-30 → v5 2026-02-05 |
| 程式 | `SamsungLabs/LittleBit`（338★，授權 **CC BY-NC 4.0，禁止商用**）；後續作 LittleBit-2（ICML 2026）只改初始化（Joint-ITQ），推論結構不變 |
| 主張 | 把權重壓到 **0.1 BPW**（每權重 0.1 bit），Llama2-13B 壓到 0.84 GB 以下 |

### 2. 方法（一句話：先低秩分解，再把分解出的因子二值化）

1. **結構**：`W ≈ diag(h) · U_sign · diag(ℓ) · V_signᵀ · diag(g)`
   - `U_sign ∈ {±1}^(d_out×r)`、`V_sign ∈ {±1}^(d_in×r)`，每個元素 1 bit。
   - 三組 FP16 縮放向量：列 `h`、行 `g`，以及新增的**潛在維度縮放 `ℓ ∈ R^r`**，用來學習每個潛在方向的重要性。
2. **前向計算**（Eq.5）：`Y = ((((X⊙g)·V_sign)⊙ℓ)·U_signᵀ)⊙h`。原本一個大 GEMM 變成「兩個小的二值矩陣乘法加三次逐元素縮放」，完全不必還原出完整的 `W`。
3. **Dual-SVID 初始化**：先做截斷 SVD 得到 `U'`、`V'`，取其正負號當作 `U_sign`、`V_sign`。再對 `|U'|`、`|V'|` 各做 rank-1 近似，拆出 `h₀`、`g₀`，並令 `ℓ₀ = ℓ_u ⊙ ℓ_v`。目的是讓 QAT 從一個已經接近原權重的位置起步。
4. **Residual Compensation**：同樣的 bit 預算拆成兩條較低秩的路徑。主路徑近似 `W`，殘差路徑近似 `W − Ŵ_pri`，兩者在 QAT 中一起訓練。
5. **訓練**：QAT 加知識蒸餾，損失為 `L = KL(logits) + 10 × MSE(中間層)`。資料是 WikiText-2 + C4，約 1B tokens，跑 5 epochs。反向傳播用 SmoothSign：前向 `sign(x)`、反向用 `tanh(100x)` 的導數。7B–14B 模型用 4×H100，QwQ-32B 用 32×A100。
6. **BPW 公式**（附錄 D）：`b = [2r(d_out+d_in) + 32(d_out+d_in) + 32r] / (d_out·d_in)`。已自算驗證：4096×4096、r=546 → 0.5499 ✓。

### 3. 主要結果（論文原數據）

| Llama2-7B（WikiText-2 PPL） | FP16 | LittleBit 0.55 | 0.3 | 0.1 | STBLLM 0.55 | STBLLM 0.3 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| PPL | 5.47 | 10.47 | 12.00 | 15.92 | 30.67 | 1.8e3 |

- 在 0.5 BPW 以下，STBLLM 會崩潰，LittleBit 仍能維持可用的 PPL。作者自己指出 0.3→0.1 之間有一道「量化懸崖」，建議甜蜜點是 **0.3–0.55 BPW**。
- 1 BPW 時並不贏專門的 1-bit 方法：Llama2-7B 9.08，OneBit 8.36、BinaryMoS 7.74。
- 速度：A100 上 70B 的 MLP 層 kernel 最高 **11.6×**；Llama2-7B 端到端解碼 **2.46×**（82.56 → 203.20 tok/s）。

### 4. 批判性分析（重點）

**4.1 比較不對等：QAT 對 PTQ**
主要對手 STBLLM 是**免訓練的 PTQ**，LittleBit 則用了約 1B tokens、5 epochs 加蒸餾的 QAT。「0.1 BPW 贏過對手的 0.7 BPW」這個頭條，有很大一部分是訓練預算的差距，不全是結構優勢。

**4.2 主要評測資料和訓練資料同源**
訓練用 WikiText-2 + C4，主要的 PPL 也是在 WikiText-2 / C4 上量。換到沒訓練過的 PTB，退化明顯更大：Llama2-7B 從 37.91 → 83.09（0.1 BPW）。

**4.3 「保留推理能力」的說法被高估了（自算）**
七項 zero-shot 任務的隨機或多數類基準平均約 **37.5%**（WinoGrande 50、OBQA 25、HellaSwag 25、BoolQ 多數類 62.2、ARC-e 25、ARC-c 25、PIQA 50）。用「高出基準的部分還剩多少」來衡量：
- Llama2-7B 0.55 BPW：(47.26−37.5)/(62.97−37.5) ≈ **38%**；0.3 BPW 約 **30%**。
- Llama3-8B 0.55 BPW：(44.38−37.5)/(70.15−37.5) ≈ **21%**。
- 多數設定的 BoolQ 低於「永遠回答多數類」的 62.2%；WinoGrande 約 51%、ARC-c 約 25%，都接近隨機。
- 附錄 F 的生成樣本作者也承認：0.1 BPW 會說蒙娜麗莎是「雕像」、把計算機科學定義成「心智科學」。

→ 比較準確的描述是：**保住了語法與表面流暢度，知識與推理大部分流失。**

**4.4 缺少最關鍵的對照組（推論）**
論文沒有和「**同樣大小的小模型 + 4-bit**」比較。Llama2-7B 在 0.3 BPW 是 0.79 GB，跟本機正在用的 Qwen3-1.7B Q4_K_M（1.1 GB）同一量級，而後者的品質幾乎可以肯定遠高於平均 45% 的 zero-shot。若以「固定位元組數下的最佳品質」來評價，LittleBit 目前很可能輸給「直接換一顆小模型」。

**4.5 「0.1 BPW」不等於整個模型 0.1 BPW（自算）**
embedding 和 `lm_head` 保持 FP16。Llama2-7B 的這兩塊是 32000×4096×2 B×2 ≈ **524 MB**，而 Transformer 區塊在 0.1 BPW 時只有約 81 MB。也就是說 0.63 GB 裡約 **83% 是沒有量化的部分**。這也是為什麼名目上 160× 的壓縮，實際只有 21×。作者在附錄 I 有承認 `lm_head` 是瓶頸。

**4.6 70B 沒有任何品質數據**
表 3 列了 70B 在 0.1–0.8 BPW 的大小（例如 0.3 BPW = 3.70 GB），但全文沒有 70B 的 PPL 或準確率。附錄 I 也說 70B 的 QAT 遇到資源限制。所以「70B 塞進 4 GB」只是算出來的大小，不是已驗證的結果。

**4.7 速度數字是挑過的**
- 11.6× 是**最大的一層**（70B MLP，8192×28672）的 kernel 數字。Llama2-7B 的 MLP 層從 0.55 到 0.1 BPW 都卡在約 **3.2×**，再壓也不會更快，因為已被 kernel 啟動與延遲的固定成本限制住。
- 端到端只有 2.46×。自算：FP16 的 82.56 tok/s × 13.49 GB ≈ 1.1 TB/s，符合頻寬受限；LittleBit 0.1 的 203 tok/s × 0.63 GB 只有約 128 GB/s。可見瓶頸已經不在讀權重，而在 FP16 的 attention / norm 和各種固定開銷。這呼應我們分析文件 §9 的論點：**權重變小後，dispatch 和其他算子的開銷就會變成主角。**
- 附錄 H.1 的 FLOPs 估算（13.0M、號稱少 7×）**只算了一條路徑**。r=431 是單一路徑的秩（自算公式吻合），加上殘差路徑約 26M，實際約 **3.5×**。
- kernel 表中的秩（70B MLP 在 0.1 BPW 用 r=640）約等於兩條路徑的秩相加（每條約 302），看起來是合併成單一路徑來計時（推論）。
- 官方 repo 的檔案樹中**找不到 CUDA kernel**（沒有 `.cu` 或 kernel 檔），論文裡的加速結果無法直接重現。

**4.8 KV cache 壓縮的說法有破綻（推論）**
論文說可以快取 r 維的潛在向量，取代完整的 K/V，壓縮約 `d_model / r` 倍（0.1 BPW 時 21.3×）。但：
- Llama 系列在 K 投影**之後**才套 RoPE。只存潛在向量的話，每個解碼步都要把所有歷史 token 的 K 重建一次再套 RoPE，計算量會隨 context 長度增加。DeepSeek MLA 正是為了這個問題才設計「解耦 RoPE」，論文完全沒提。
- 表 4 標明是「Estimated」，沒有實測。

**4.9 小地方**
- 殘差路徑在 OPT-1.3B / 0.1 BPW 反而變差（PPL 60.0 vs 48.5），作者仍然全面採用。
- 第 5 節的交叉引用寫成「Section 4.3」，應為 Table 4。
- 附錄 A 的 Claim/Proposition 只是啟發式說明（「might」「likely」），不是證明。

### 5. 真正的貢獻（持平評價）

1. **在 0.3–0.55 BPW 區間確實是目前最穩的方法**，相對 STBLLM 的崩潰是質的差別。
2. **「改變結構而不是改變型別」**：這補充了我們分析文件 §9.2 的論點 1。我們當時說在 4-bit 級別「幾乎沒有再壓縮的空間」，那是指 block 量化型別的上限；LittleBit 改走低秩加二值化，繞過了這個上限，代價是品質大幅下降。
3. `ℓ` 潛在縮放加 Dual-SVID 初始化是乾淨、可移植的設計。LittleBit-2 證明初始化還有改進空間。

### 6. 與本專案（hetero-llm / ggml）的關係

| 問題 | 結論 |
| --- | --- |
| 本機能自己訓練嗎？ | ❌ 7B 需要 4×H100 跑約 1B tokens；本機 RTX 4050 6 GB 完全不可行 |
| 有現成權重嗎？ | ⚠️ README 的範例用的是佔位名稱 `username/littlebit-llama-7b-0.1bpw`，**沒有列出官方釋出的權重** |
| llama.cpp 能跑嗎？ | ❌ 目前沒有支援。但**理論上不必新寫 kernel**（推論、待驗證）：`U_sign`、`V_sign` 可用 ggml 現有的 `Q1_0`（18 B / 128 元素 = 1.125 bpw，scale 設為 1）存放，`h`、`g`、`ℓ` 存為 F16 向量。計算圖就是 `mul → mul_mat → mul → mul_mat → mul`，再加上殘差路徑的 `add`。工作量在於新增模型架構和轉換器，而非新後端。需先確認 `Q1_0` 在 CPU / CUDA 的 `mul_mat` 支援度。 |
| 對本機 CPU 有吸引力嗎？（自算） | 以實測有效頻寬約 26 GB/s 估算：Llama2-7B 在 0.3 BPW 時每 token 約讀 505 MB（`lm_head` 262 MB + 區塊 243 MB），上限約 50 tok/s，比 Qwen3-1.7B Q4_K_M 的 24 tok/s 快。但品質差距（§4.3–4.4）讓這個速度沒有意義。 |
| 對 6 GB VRAM 有吸引力嗎？ | 只在 70B 等級才有意義（0.3 BPW = 3.70 GB，落在 4896 MiB 的預算內），但 **70B 沒有品質數據**（§4.6）。 |
| 授權 | 程式碼 CC BY-NC 4.0、論文 CC BY-NC-ND 4.0 → 只能用於研究，不可商用 |

**結論**：值得追蹤，目前不值得投入。對本專案最有價值的是三個觀念：(1) 低秩加二值化是突破「4-bit 下限」的另一條路；(2) 權重壓到極小之後，瓶頸會轉移到 FP16 的 embedding / `lm_head` 和 dispatch 開銷；(3) 評估量化方法時，應以「**同樣位元組數下的小模型 + 4-bit**」作為基準。

**觸發重新評估的條件**：官方或社群釋出 ≥30B 的 LittleBit 權重**並附品質數據**，或 llama.cpp 開始支援低秩二值化的線性層。

## 目標釐清：異質硬體協同運算 + 超小模型達到商業模型水準

**使用者陳述**

> 我的目的希望在任何可用於計算的硬體如 CPU GPU NPU 都可以組合起來一起運算，並且使用超小的模型可以達到目前商業模型的水準

### 1. 拆成兩個子目標，可行性不同

| 子目標 | 照字面做 | 換個做法 |
| --- | --- | --- |
| A. 所有硬體一起算 | ❌ 單一請求的逐 token 解碼無法加總多個裝置的算力 | ✅ 把工作改成「可平行的形狀」，就能加總 |
| B. 超小模型 = 商業水準 | ❌ 單一小模型在「廣泛知識」上做不到 | ✅ 「小模型 + 系統」在**指定任務**上可以接近 |

### 2. 子目標 A：硬體什麼時候真的能「加起來」

已確立的事實：解碼受記憶體頻寬限制，每個 token 依序經過每一層。把模型切在 CPU 和 GPU 上時，總時間是兩者**相加**而不是取最大值（hw-autoconfig §6.5.2）。本機實測 CPU 解碼增加執行緒也不會更快（約 24 t/s 持平）。

能讓多種硬體**同時做有用功**的只有以下五種形狀：

| 形狀 | 各硬體分工 | 是否真平行 | 本機可行性 |
| --- | --- | --- | --- |
| 1. 容量合併（`-ngl`/`-ot`） | GPU 放一部分層，CPU 放其餘 | 否，只換來放得下 | ✅ 已具備 |
| 2. MoE 專家分置 | 注意力層與共享層在 GPU，稀疏專家在 RAM/CPU | 部分 | ✅ 需 CUDA build |
| 3. 投機解碼 | 小 draft 模型猜、大模型一次驗證多個 token | 是（draft 與驗證可重疊） | ✅ 需 CUDA build |
| 4. **平行取樣 / 批次** | 同一問題取 N 條推理，或同時處理多個請求，各裝置分攤 | **是**，批次運算受算力限制，算力可以相加 | ✅ |
| 5. 任務管線 | NPU 負責 embedding/rerank，CPU 負責檢索與工具，GPU 負責生成 | 是（行程級） | ⚠️ 本機無 NPU |

**關鍵洞察**：子目標 A 與 B 在第 4 種形狀上交會。小模型要逼近大模型，最有效的手段是**推論時多花算力**（多條取樣、自我驗證、投票）。這類工作是批次形狀、受算力限制，正好是異質硬體**能夠相加**的情境。所以「讓所有硬體一起算」最有價值的用途，不是讓單一回答變快，而是讓小模型**在同樣時間內想得更多**。

### 3. 子目標 B：「小模型 = 商業水準」的物理限制

- **知識容量和參數量成正比**（文獻經驗值約每參數 2 bit 的事實知識；屬於引用的研究結論，未在本機驗證）。商業模型推估有數千億以上參數，1–4B 的模型裝不下同樣多的世界知識。LittleBit 也從反面證明：極端壓縮最先失去的就是知識（§4.3、附錄 F）。
- **推理能力則不完全取決於大小**：小模型經過蒸餾與強化學習，在數學、程式等**可驗證任務**上可以很接近大模型，再加上推論時的計算量還能更進一步。

→ 正確的架構是把三件事分開處理：

| 能力 | 不放在模型權重裡，改放在 | 本機元件 |
| --- | --- | --- |
| 世界知識 | 檢索（RAG：向量庫 + rerank） | NPU/CPU 引擎 + embedding |
| 精確計算 / 事實查證 | 工具（程式執行、搜尋、計算機） | CPU |
| 推理品質 | 推論時計算（平行取樣 + 驗證器 + 投票） | GPU + CPU 批次 |
| 領域專長 | 小型 LoRA 微調，依任務路由 | GPU |
| 容量 | MoE（總參數大、每次啟用少） | RAM 放專家 + GPU |

**MoE 是本機最有潛力的路線（推論，待驗證）**：例如 30B 總參數、3B 啟用的模型，具備 30B 等級的知識容量，每個 token 卻只需讀約 3B 參數。本機的總預算是 RAM 12010 MiB + VRAM 4896 MiB ≈ 16.5 GiB。Q4_K_M 大約超出預算，Q3 級量化可能放得下。解碼時每 token 約讀 1.5–2 GB；以 CPU 實測頻寬約 26 GB/s 估算，約 **10–15 t/s**。這是在本機上「用小算力拿到大模型品質」最務實的方式，比 LittleBit 那種極端壓縮實際得多。

### 4. 「商業模型水準」必須先定義成可量測的目標

沒有評測集，就無法判斷是否達標。建議：
- 選 3–5 個**實際要用的任務**（例如中文問答、程式、文件摘要、工具呼叫）。
- 每個任務準備 30–100 題，附參考答案或評分規則。
- 用一個商業模型的分數當作 100% 基準線，追蹤本機系統達到幾 %。

### 5. 建議路線（接續 hetero-runtime 計畫）

| 階段 | 內容 | 驗收 |
| --- | --- | --- |
| R0 | 建立評測框架與題庫，並量測商業模型的基準分數 | 每次改動都能自動算出「達成 %」 |
| R1 | 安裝 CUDA toolkit → `build-cuda`（目前的阻塞點） | `primary_device = cuda0` |
| R2 | MoE 專家放 CPU、注意力放 GPU，用 calibrator 找最佳切法 | 30B 級 MoE 在預算內穩定跑出 ≥10 t/s |
| R3 | 投機解碼 + 平行取樣（N 條）+ 投票/驗證 | 同樣時間內分數提升，且 GPU/CPU 同時有負載 |
| R4 | RAG + 工具呼叫 + 任務路由（LoRA） | 知識題分數大幅提升 |
| R5 | NPU 接手 embedding/rerank（需 Core Ultra 機器） | 同 hetero-runtime S4 |
| 觀察 | 極端量化（LittleBit 等） | 有釋出權重且附品質數據時再評估 |

1. 「商業水準」要以哪些任務來衡量？
2. 是否允許「本機不確定時轉交雲端模型」作為最後防線，還是必須 100% 本機運行？

## 決策：以 LittleBit 形式的模型為核心，最小硬體成本做最大的通用模型

**使用者回覆**

> 1. 衡量任務：是的（中文問答、寫程式、文件摘要、工具呼叫），後面還包括一些重要元素，相關資料之後再補齊。
> 2. 本機沒把握時，可以轉交雲端模型處理，這是必需的。
> 簡單說，我想要的就是以最小硬體成本做出最大的多功能通用模型，這個模型是 LittleBit 的狀態形式。

**已確立的決策**

| 項目 | 決策 |
| --- | --- |
| 評測任務 | 中文問答、寫程式、文件摘要、工具呼叫；其他要素待補 |
| 雲端轉交 | **必要元件**：本機信心不足時轉交雲端 |
| 模型形式 | LittleBit（低秩分解 + 二值因子 + 多維縮放） |
| 目標函數 | 在最小硬體成本下，取得最大的通用能力 |

### 1. 官方程式碼查證（`SamsungLabs/LittleBit`）

- **支援模型**：OPT、Llama 1/2/3、Phi-4、Qwen2.5/QwQ、Gemma 2/3、**Qwen3**。程式碼中找不到 MoE / expert 的處理，可視為只支援 dense 模型。
- **前向計算**（`quantization/modules/littlebit.py:118`）：`((((x*v2) @ Vqᵀ) * (v1*u2)) @ Uqᵀ) * u1`，主路徑和殘差路徑各算一次再相加。實作上 `ℓ` 是用 `v1*u2` 兩個向量相乘，與論文寫法等價。
- **儲存格式**：`binary_packer` 把 ±1 打包成 `int32`（每 32 個元素一個字），state_dict 存的是 `U_packed`/`V_packed`/`U_R_packed`/`V_R_packed` 加上 FP16 向量 → **可以寫轉換器重新打包成 ggml 格式**。
- 兩條路徑在第一步各自乘上自己的 `v2`，**無法合併成一次矩陣乘法**。每個線性層在 ggml 計算圖中約有 11 個節點，因此 dispatch 開銷會變重要（呼應分析文件 §9.3(c)）。

### 2. 第一個必須正視的問題：詞表層會吃掉所有壓縮收益（自算，詞表大小待確認）

Qwen3 的詞表約有 15.2 萬個 token。以 Qwen3-8B（hidden 4096）為例，若照論文做法讓 embedding 與 `lm_head` 保持 FP16：每塊約 1.24 GB，兩塊共約 **2.5 GB**；而 Transformer 區塊在 0.55 BPW 時只有約 **0.47 GB**。

→ **對策**：區塊用 LittleBit，詞表層改用 ggml 現有的 K-quant（embedding Q4_K、`lm_head` Q6_K 或 Q4_K）。合計約 **1.2 GB**。embedding 每個 token 只讀一列，實際解碼時讀取的主要是 `lm_head` 加區塊。這是 LittleBit 原論文沒做、而我們做得到的組合。

### 3. 決定成敗的實驗 E1：同樣位元組數下，誰比較強？

LittleBit 只有在「**同樣大小的檔案，比直接用小模型 + 4-bit 更聰明**」時才有存在價值。論文沒有做這個比較，所以必須由我們自己驗證：

| 組別 | 模型 | 大約大小 |
| --- | --- | --- |
| A（LittleBit） | Qwen3-8B @ 0.55 BPW + 詞表 K-quant | ~1.2 GB |
| B（對照） | Qwen3-1.7B Q4_K_M（本機已有，24 t/s） | 1.1 GB |
| A'（LittleBit） | Qwen3-14B @ 0.3 BPW + 詞表 K-quant | ~1.5–2 GB（待算） |
| B'（對照） | Qwen3-4B Q4_K_M | ~2.5 GB |

- 用 R0 的四類任務題庫評分。
- **判準**：A 勝過 B，才繼續走 LittleBit 路線；A 輸給 B，代表在現有技術下 LittleBit 形式不划算，資源應轉向「小模型 + 系統」。這是一個便宜又能及早止損的關卡。

### 4. 成本估算（推論，誤差約 ±2 倍）

- **訓練 Qwen3-8B @ 0.55 BPW**：teacher 前向約 1.6e19 FLOPs；student 的前向約為 dense 的 b 倍（0.55×），含反向傳播約 2.6e19。合計約 4.2e19 FLOPs，以 H100 約 35% MFU 計算約 **33 H100 小時**，雲端租用約 **US$70–100 / 次**。若含學習率掃描（論文掃了 3 個以上），約 US$300。
- **本機能做的**：用 Qwen3-0.6B 跑一次縮小版 QAT，**驗證整條流程**（訓練 → 打包 → 轉換 → ggml 推論 → 評測）。PyTorch 的 CUDA wheel 自帶 runtime，**不需要 `nvcc`** 就能用 RTX 4050 訓練。6 GB VRAM 很緊（teacher 約 1.2 GB + 潛在因子與 Adam 狀態約 3 GB），需要短序列加 gradient checkpointing，必須實測才知道放不放得下。
- **推論端（目標）**：本機 CPU 加 GPU 就能跑；每 token 讀約 1 GB，CPU 理論上限約 25 t/s，GPU（192 GB/s）理論上限超過 100 t/s（未計固定開銷）。

### 5. 整體架構（LittleBit 核心 + 系統）

```
請求 ─▶ gateway ─▶ LittleBit 核心模型（GPU/CPU，ggml）
                 │     └─ N 條平行取樣（GPU+CPU 批次，硬體可加總）
                 │            └─ 一致率 / 驗證器分數 = 信心
                 ├─▶ RAG（NPU/CPU：embedding + rerank）補知識
                 ├─▶ 工具（CPU：程式執行、搜尋）補精確性
                 └─▶ 信心 < 門檻 ─▶ 雲端模型（必要防線）
```

- **信心訊號的來源**：N 條取樣的答案一致率（工具呼叫看參數是否一致、程式看測試是否通過）。這讓「平行取樣」同時做到兩件事：提升品質，以及判斷是否該轉交雲端。
- **雲端轉交比例**是成本的核心指標：本機能吃下的比例越高，越接近目標。

### 6. 修訂後路線

| 階段 | 內容 | 位置 |
| --- | --- | --- |
| R0 | 四類任務題庫 + 評分器 + 雲端模型基準分數 | 本機 |
| **L0** | Qwen3-0.6B LittleBit 縮小版 QAT，打通訓練 → 打包流程 | 本機 RTX 4050 |
| **L1** | 轉換器：LittleBit state_dict → GGUF（`Q1_0` 存 ±1、F16 存縮放向量、詞表層用 K-quant）；在 llama.cpp 加入 LittleBit 線性層的計算圖 | 本機 |
| **E1** | Qwen3-8B @ 0.55 的 QAT → 同位元組對照評測 → **決定是否繼續** | 雲端訓練 + 本機評測 |
| R1 | CUDA build | 本機 |
| R3 | 平行取樣 + 一致率信心 + 雲端轉交 | 本機 |
| R4 | RAG + 工具 | 本機 |
| 後續 | 更大的 base（14B/32B）、LittleBit-2（`--use_itq`）、自寫二值 kernel 消除 dispatch 開銷 | — |

### 7. 風險

1. **E1 可能失敗**：論文的 zero-shot 數據（§4.3 分析）顯示，0.55 BPW 時知識流失嚴重，輸給同大小小模型的機率不低。這正是 E1 要放在最前面的原因。
2. **授權**：LittleBit 程式碼為 CC BY-NC 4.0。若未來要商用，需自行實作（方法本身沒有專利聲明，但需另行查證）。
3. **Q1_0 在 ggml 的 `mul_mat` 支援度未驗證**：若不支援，L1 需要自寫 kernel，工作量大增。
4. **詞表 K-quant 未參與 QAT**，可能帶來額外損失；必要時可在 QAT 中把詞表層也納入（屬於 LittleBit 的延伸）。

**狀態**：只有分析與規劃，沒有修改任何程式。

| Self-Rewarding | **只做過 70B**；early stopping 用 Claude 2 判定；ARC-c、NQ 下降；回答長度 2.3× |
| ADAS | 知識型任務（MMLU/GPQA）增益很小；弱模型（Haiku）絕對增益小；**成本主要花在評估** |
| Gödel Agent | 不受限版本會**自己改去呼叫 GPT-4o**（等於繞過限制）；14% 試驗結果比起點更差 |
| Survey | 自我修正約在 **>22B** 才出現；超過 3 輪難以再提升；模型崩潰 |

**八項跨論文發現 → 計畫的八條原則（P1–P8）**

1. 驅動進化需要大模型 → **雲端當老師、評審、元智能體；LittleBit 只當學生與執行者**
2. 外部驗證是共同關鍵 → **新增 V0 驗證器函式庫**，作為飛輪的地基
3. 進化無法創造知識 → **RAG 優先**；E1 把知識題與推理/工具題**分開評分**
4. 蒸餾勝過自我訓練 → **雲端轉交的內容就是訓練資料**
5. 約 3 輪就停滯 → 每輪從凍結核心重訓 LoRA，最多 3 輪
6. 只用正樣本 SFT 不一定有效 → 驗證過的資料用 SFT，評審打分的資料用 DPO
7. 普遍有退步與長度膨脹 → 回歸關卡涵蓋四類任務 + 長度 + 延遲
8. 獎勵駭客已實際發生 → 自我修改的元件不得觸碰評分器、預算、轉交門檻

**架構的新設計：四層分層轉交**（源自 Self-Refine 的混合修正）

第 0 層純本機 → 第 1 層依驗證器錯誤訊息在本機重試 → 第 2 層**只請雲端給回饋或修正**（部分轉交，比整題便宜）→ 第 3 層雲端完整回答。各層比例就是成本儀表板。

**9 篇的採用決策**：主力 ReST-EM；直接採用 Voyager 技能庫、ADAS（雲端元智能體 × 本機評估）；改造後採用 STaR、Self-Refine、Self-Rewarding（都改為雲端提供判斷）；SPIN 作為第二階段；Gödel Agent 延後到最後，只在沙盒中進行。

**修正先前的說法**

- 先前引用 Huang et al. 2023〈LLMs Cannot Self-Correct Reasoning Yet〉，但本次沒有讀到原文 → 改以 Survey 的敘述為準。

## 決策：「向強者學」是自我進化的主幹之一

**使用者指令**

> 「向強者學」的原則也很重要，這是自我進化的一條路
