## 1. ScaleQ-1.58 / AYOT（arXiv 2608.01078，Intel Labs China，2026-08 預印本）

**方法 [原文]**：三值 PTQ = CAT-Q（可學習的軟三值化，群組 scale 與門檻，跨層滑動視窗重建）+ AYOT 校準：取領域題目（MetaMathQA、OpenCodeInstruct），**由待量化的 FP 模型自己生成推理過程與答案**，拼成校準上下文。預設 4M tokens、60 epochs、序列長度 2048。

**校準方式消融（Qwen3-4B；Math-500 / GSM8K / Omni / HumanEval+ / MBPP+）[原文]**
| 校準資料 | 結果 |
| --- | --- |
| WikiText2 | 0 / 2.65 / 0.43 / 0 / 0 |
| C4 | 0 / 14.48 / 2.71 / 0 / 0 |
| 領域問答（原始答案） | 24.2 / 28.7 / 5.0 / 17.9 / 11.4 |
| **DeepSeek-R1-671B 生成的推理過程** | 31.8 / 30.8 / 7.0 / 16.5 / 14.3 |
| **模型自己生成（AYOT）** | **58.4 / 61.6 / 14.9 / 54.0 / 39.2** |

→ **壓縮階段：學生應該模仿「自己的 FP 版本」，而不是更強的老師**。這修正了計畫的 P4（蒸餾優先），P4 只適用於壓縮之後的能力提升階段。**[推論]**

**主結果（FP16 → 三值，4M tokens）[原文]**
| 模型 | Math-500 | GSM8K | HumanEval+ | MBPP+ |
| --- | --- | --- | --- | --- |
| BitNet b1.58 2B4T（4T tokens 從頭訓練） | 43.4 | 58.4 | 38.4 | 37.0 |
| Qwen3-1.7B | 90.8 → 38.6 | 84.1 → 54.4 | 76.2 → 34.1 | 54.0 → 33.3 |
| Qwen3-4B | 96.8 → 58.4 | 88.1 → 61.6 | 85.4 → 54.0 | 61.9 → 39.2 |
| Qwen3-8B | 96.8 → 63.0 | 88.9 → 71.7 | 87.2 → 54.9 | 63.5 → 44.7 |
| **Qwen3-14B** | 97.2 → **76.8** | 91.4 → **79.2** | 86.6 → **74.4** | 64.3 → 50.3 |
| **Qwen3-32B** | 96.8 → **85.2** | 93.6 → **87.3** | 87.2 → **84.2** | 66.9 → 54.5 |
| Qwen3-30B-A3B（MoE） | 97.6 → 76.8 | 94.8 → 85.0 | 86.6 → 60.4 | 63.0 → 45.0 |

- 模型越小越敏感；**同參數量下 MoE 比 dense 更敏感**。
- 校準 tokens 從 256K 增加到 16M，效果持續上升、尚未飽和（Qwen3-4B 在 16M 時 Math-500 達 66.2）。
- 序列長度 4096 優於 2048（Math-500 58.4 → 68.6）。

**領域專精化（表 8，Qwen3-4B）[原文]**
| 校準資料 | 數學/程式平均 | 困惑度 | 常識推理 | ProofWriter |
| --- | --- | --- | --- | --- |
| C4（通用） | ≈3 | **25.40** | **58.17** | 1.38 |
| 數學 / 程式 | ≈46 | 35.34 | 53.23 | 39.50 |
| + ProofWriter 訓練樣本 | ≈46 | 28.64 | 57.05 | **83.92** |

→ **校準資料決定了三值模型擅長什麼**；混合多領域可以平衡。

**成本（8×A100，60 epochs，4M tokens）[原文]**：1.7B 4 小時、4B 8 小時、8B 20 小時、14B 32 小時、32B 65 小時、30B-A3B 56 小時。
→ 8B 約 160 A100 小時、14B 約 256 A100 小時 **[自算]**，**比我們估的 LittleBit QAT（約 33 H100 小時）還貴**。「PTQ」不等於便宜。

**部署（llama.cpp，Qwen3-4B，batch 1，生成 512 tokens）[原文]**
| 格式 | 大小 | CPU t/s | GPU t/s |
| --- | --- | --- | --- |
| Q4_K_M | 2.32 GB | 19.31 | 225.91 |
| Q2_K | 1.55 GB | 23.84 | 268.51 |
| **三值（CPU `TQ1_0` / GPU `TQ2_0`）** | **1.01 / 1.17 GB** | **37.35** | **320.34** |

> **更正（2026-11-14，R19.4）**：本機 llama.cpp `93cf736` 的 CUDA 後端**不支援 `TQ2_0`/`TQ1_0` 矩陣乘法**（`test-backend-ops` 實測），上表的 GPU 320 t/s 用本機版本無法重現。

**限制 [原文]**：程式碼標示「will be available」（`IntelChina-AI/BitTern`），v1 時尚未釋出；適用於多樣三值模型的高效 kernel 仍然有限；與 FP16 的差距仍大。

## 2. BITCOS（arXiv 2609.16338，Intel，2026-09）

- 量測 29 個三值模型，**零值比例最高達 51.5%**；提出「存在位元圖 + 壓縮符號向量」格式，每權重 (2 − z) bits，最低 1.485 bpw。在 29 個模型中有 26 個比 5-trit 打包（1.625 bpw）更省空間 **[原文]**。
- **公開三值模型清單 [原文]**：BitNet b1.58 2B4T；Prism ML Ternary Bonsai 1.7B/4B/8B/27B（HF `prism-ml`，附自家 llama.cpp fork）；CAT-Q 量化的 Qwen3 1.7B–235B（ICML 2026，arXiv 2606.26650，**是否公開未確認**）；ParetoQ 125M–1.5B；TriLM 99M–3.9B；**Maple 20B-A1B 三值 MoE 推理模型**（HF `deepgrove/maple-preview`）；OpenBMB BitCPM-CANN 0.5B–8B。
- 平台包含 **Arrow Lake 285K（8P+16E，AVX2，與本機同屬 Intel 混合架構的用戶端 CPU）**：llama.cpp `TQ1_0` 比 `Q2_0` **快 1.66–1.68×**；BITCOS kernel（在 vLLM CPU backend 中）又比 llama.cpp `TQ1_0` 快 1.46–1.74× **[原文]**。
- 頻寬充裕、核心少的平台（Lunar Lake）屬於指令受限，換格式沒有好處 **[原文]**。

## 3. BitNet Distillation（arXiv 2510.13998，微軟，2025-10）

- **只針對單一下游任務**：MNLI、QNLI、SST-2（GLUE 分類）與 CNN/DailyMail 摘要 **[原文]**。**沒有評估一般對話、知識問答、程式、工具呼叫。**
- 三階段：(1) 在 attention 輸出投影與 FFN down 投影前插入 SubLN；(2) **持續預訓練 100 億 tokens**（FALCON）；(3) 任務微調 = CE + logits 蒸餾（τ=5）+ MiniLM 注意力關係蒸餾（**只取單一、偏後段的一層**）**[原文]**。
- 結果：與 FP16 相當（MNLI 0.6B 88.17 vs 88.01；4B 91.40 vs 91.48；摘要平均 27.44 vs 27.58）；0.6B 在 CPU（16 執行緒）跑 1135 vs 427 t/s、記憶體 0.11 vs 1.20 GB **[原文]**。
- 消融（0.6B MNLI）：什麼都不加 74.09 → +SubLN 76.30 → +SubLN+持續預訓練 86.73 → 全部 88.17 **[原文]**。
- **更大的老師效果更好**：用 Qwen3-1.7B/4B 當老師教 0.6B 三值學生，甚至超越同尺寸的 FP16 **[原文]**。
- 硬體：8×AMD MI300X **[原文]**。

**[推論]** 可用於**文件摘要專精模型**（論文正好做了摘要），不適合當通用核心。成本大頭在 100 億 tokens 的持續預訓練。

## 4. Dovetail（arXiv 2412.18934，國防科大，EMNLP 2025）

- draft（EAGLE-2 式 head，1–6 層 Transformer + 動態門控融合）放 GPU；**target 放 CPU**，一次前向平行驗證 γ 個候選 **[原文]**。
- 關鍵分析：target 在 CPU 時，平行驗證時間 T_V(γ) 是瓶頸（CPU 平行度低），所以要**減少 draft token 數**（16 個，筆電 7 個；EAGLE-2 原本 60 個），並**加深 draft 模型**（因為 T_D/T_T 趨近 0）**[原文]**。
- draft 需針對每個 target 訓練：8×A800 約 1 天 **[原文]**。
- **基準的注意事項 [原文]**：伺服器上 target 用 **PyTorch FP32**（7B 純 CPU 只有 2.14 t/s）；筆電用 PyTorch 動態 8-bit。
- 結果 [原文]：2080S + LLaMA2-7B HumanEval 3.78×（target 22 層在 CPU、10 層在 GPU）；3090 + 13B 10.14×；**筆電（i5-9300H + GTX 1050）只有 1.74–1.79×**（3.65 → 6.35 t/s）。
- 實作是 PyTorch，不是 llama.cpp **[原文]**。

**本機查證**：`vendor/llama.cpp/common/arg.cpp` 有 `--spec-draft-device`（`-devd`）、`--spec-draft-ngl`（`-ngld`）、`--spec-draft-threads`、`--spec-draft-cpu-mask/range`、`--spec-draft-override-tensor`（`-otd`）、`--spec-draft-n-max/min`、`--spec-draft-p-min` → **Dovetail 的拓撲只靠參數就能組出來**（需要 CUDA build）。若 draft 用同家族小模型（如 Qwen3-0.6B），就不必另外訓練 EAGLE head。

**[推論] 何時值得用**：target 放不進 VRAM 預算（4896 MiB）時。例如 Qwen3-32B 三值約 6.8 GB **[自算]**（32B × 1.69/8，未含詞表層）→ 放 RAM（預算 12010 MiB 內），draft 放 GPU。以 CPU 實測頻寬約 26 GB/s 估算，基準約 3.8 t/s，若加速 1.7–2× 約 6.5–7.5 t/s **[推論，待量測]**。

## 5. Physics of Language Models 3.3（arXiv 2404.05405，ICLR 2025）

**[原文]**（合成的人物資料，GPT-2 架構）
- 充分訓練（每筆知識曝光 1000 次）→ **2 bit/參數**（7B ≈ 140 億 bits，作者估計超過英文維基 + 教科書）。
- 只曝光 100 次 → 1 bit/參數；此時 LLaMA/Mistral 比 GPT-2 低 1.3×，原因是 gated MLP。
- **量化（Result 8，使用 auto_gptq）**：int8 沒有損失；**int4 降到 0.7 bit/參數**。作者建議「高品質的 int4 模型可能需要在訓練時就量化」；沒有測試其他量化方法。
- **MoE（Result 9）**：32 個專家（推論時只用 8.8% 參數），容量只少 **1.3×**。
- 垃圾資料：有用 : 垃圾 = 1 : 7 時，容量損失 20×；在有用資料前加上網域標記，可恢復到 2×。

**[自算 / 推論]**
- 以「每個儲存位元能裝多少知識」計：int8 = 2/8 = 0.25；GPTQ int4 ≈ 0.7/4.5 ≈ 0.16。
- 這代表：**在相同位元組數下，Q8 的較小模型可能比 Q4 的較大模型記得更多**。注意事項：資料是合成的、方法是 GPTQ 而非 K-quant、沒有測 QAT。這正是 E0/E1 要實測的問題。
- MoE 的結果支持「總參數大、每次啟用少」是用小算力保住知識的好方法。

## 6. AutoMix（arXiv 2310.12963，NeurIPS 2024）

- 三步驟 [原文]：小模型回答 → **同一個小模型**以 few-shot 判斷「答案是否與上下文一致」（蘊含任務；高溫取樣 k 次估計機率）→ 路由器決定保留或轉交。
- 路由器：門檻法或 **POMDP**（觀察值 = 驗證機率，用 KDE 建模，獎勵 = 表現 − λ × 成本）；**50 筆資料**就能學；每次查詢 <1 ms；**能學會「無解的題目不要轉交」**以省錢 [原文]。
- 指標 IBC（每單位成本的增益）[原文]。成本比低到 1:10 時就開始有效益 [原文]。
- 小模型：Mistral-7B、Llama2-13B、GPT-3.5；大模型：GPT-4 [原文]。
- **作者自述限制**：只適用對話與有上下文的推理，**不適用事實問答與常識推理** [原文]。

**[推論]** 對應我們的**文件摘要**與**接上 RAG 的中文問答**（都有上下文可對照）。但用來驗證的模型至少要 7B 等級；我們的超小核心未必能勝任，可能要由另一個驗證模型負責。

## 7. RouteLLM（arXiv 2406.18665，ICLR 2025）

- **生成前**就路由（每個請求只呼叫一個模型，不增加延遲），與串接式（FrugalGPT、AutoMix）不同 [原文]。
- 指標：PGR、APGR（曲線下面積）、CPT(x%)＝要彌補 x% 品質差距，最少需要多少比例轉交強模型 [原文]。
- 資料：8 萬筆 Chatbot Arena 對戰（模型分 10 個等級）＋ MMLU 驗證集約 1500 筆標準答案，或約 12 萬筆 GPT-4 評審標註（約 US$700）[原文]。
- 路由器：相似度加權排序（不用訓練）、矩陣分解（8 GB GPU 即可）、BERT、Llama-3-8B 分類器 [原文]。
- 結果：MT-Bench 上矩陣分解 APGR 0.802、CPT(50%) 13.4%（隨機為 49%）；**只用 Arena 資料時，MMLU 接近隨機**，加入同領域標準答案後才改善；省錢最多 3.66×（MT-Bench）、GSM8K 1.49× [原文]。
- **Arena 資料 81% 英文、只有 3.1% 中文** [原文]。

**[推論]** 我們的軌跡記錄器（本機答案 vs 雲端答案 + 驗證或評審結果），正好就是論文中的同領域偏好資料。中文路由器必須用自己的資料訓練。

## 8. LittleBit-2（arXiv 2603.00042，Samsung，ICML 2026）

- 理論 [原文]：LLM 權重的奇異值呈重尾分布（衰減率 γ 有 90% 落在 0.19–0.47），此時「低秩二值」勝過「極低秩 FP」。
- 問題：SVD 的奇異向量分布尖銳，對 sign() 最不利 → 解法：潛在旋轉 + Joint-ITQ，把潛在向量對齊到超立方體頂點；**只改初始化，推論零額外成本** [原文]。
- **主結果（Llama-3 8B；WikiText-2 困惑度 / 5 項 zero-shot 平均 / 總記憶體）[原文]**

| 方法 | bpp | 困惑度 | zero-shot | 總記憶體 |
| --- | --- | --- | --- | --- |
| FP16 | 16 | 6.10 | 72.97 | 16.1 GB |
| **EfficientQAT** | **2** | **9.80** | **63.49** | **4.1 GB** |
| OneBit | 1.0 | 13.09 | 52.23 | 3.0 GB |
| LittleBit-2 | 1.0 | 11.53 | 57.33 | 3.0 GB |
| LittleBit-2 | 0.55 | 14.01 | 51.33 | 2.6 GB |
| LittleBit-1 | 0.1 | 26.11 | 41.80 | 2.2 GB |
| LittleBit-2 | 0.1 | 23.74 | **41.64** | 2.2 GB |

- Gemma-3 27B @ 0.1 bpp：FP16 79.48 → LB2 47.06 [原文]。
- **沒有 Qwen 結果、沒有報告訓練成本、推論速度數字沿用第一代論文** [原文]。

**[推論]**
1. 0.1 bpp 時 LB2 在 zero-shot 上沒有進步，主要的進步在 1.0 / 0.55 bpp。
2. **總記憶體欄位說明一切**：Llama-3 8B 在 0.55 bpp 的總大小是 2.6 GB，其中區塊只占 0.5 GB，詞表層占了 2.1 GB（Llama-3 詞表 128K）。
3. 在大約 3–4 GB 的預算下，EfficientQAT 2-bit（63.49）與三值 PTQ 都明顯優於 LittleBit 系列。

## 9. Agent Workflow Memory（arXiv 2409.07429，CMU / MIT，ICML 2025）

- 工作流程 = 自然語言描述 + 步驟（環境狀態描述、推理、可執行動作）；由 LM 歸納出「子程序」層級的流程，並把具體值抽象成 `{placeholder}` [原文]。
- 離線（從有標註的範例歸納）或線上（從自己的軌跡歸納，由 LM 評審判斷是否成功）；工作流程可以疊加成更複雜的流程 [原文]。
- 模型：GPT-4 / GPT-3.5，溫度 0 [原文]。
- WebArena：比 BrowserGym 高 12.0 分（相對 +51.1%），**勝過人類專家寫的工作流程 7.6–7.9%**；Mind2Web 跨網站 / 跨領域 +8.9–14.0 分；抽象化的工作流程勝過直接檢索具體範例 [原文]。
- 風險：線上模式會從自己可能錯誤的預測中歸納，產生錯誤流程並拖累表現 [原文]。

**[推論]** V1 技能庫採離線模式：由雲端從**經過驗證的**軌跡歸納工具呼叫流程（含 placeholder），本機模型只負責使用。

## 10. ToolRM（arXiv 2509.11963，IBM，2026-01 v2）

- FC-RewardBench：1500 題 BFCL-v3，錯誤多半很細微（參數值錯 650、函式名錯 403、函式數量錯 245）[原文]。
- 既有獎勵模型表現差（Themis 45%；純 schema 驗證更差）；LLM 評審超過 80%，但需要 70B–685B [原文]。
- ToolRM 1.5B/7B/14B（以 Qwen2.5-Instruct 為底）：訓練資料 18 萬筆，**錯誤樣本由 11 個寬鬆授權的開源模型產生**（Qwen2.5、Granite），題目先做名稱混淆 [原文]。
- **ToolRM-1.5B 準確率 81.88%**（勝過 gpt-oss-120B 當評審）；拿掉名稱混淆降到 68.25；**只用 ≤2B 的小模型產生錯誤樣本也有 81.01** [原文]。
- **Best-of-32（溫度 0.6）+ ToolRM-14B [原文]**：
  - Qwen3-0.6B：39.5 → **64.4**（超過 Qwen3-32B 貪婪解碼 63.8、xLAM-2-70B 63.6）
  - Qwen3-8B：→ 70.5
  - Qwen3-1.7B（BFCL）：整體 +5.3、Non-Live AST +9.6、Live AST +8.7
  - 32B 以上的模型增益遞減
- 用 ToolRM 篩出前 50% 的資料訓練，效果 ≥ 用全部資料；以 ToolRM 為獎勵做 GRPO，效果追平需要標準答案的獎勵 [原文]。

**[推論]**
- 這是「**超小生成器 + 平行取樣 + 驗證器 ≈ 大模型**」最有力的實證（至少在工具呼叫上）。
- 32 條取樣是批次工作，正好讓 GPU 與 CPU 加總算力；驗證器（1.5B）可以放在另一個裝置上平行評分。
- 訓練配方只用開源模型，**沒有服務條款問題**，可以照做出中文版本。

### 11.2 核心形式的選項（需要你決定，見下方）
| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| A. 維持 LittleBit | 位元數最低（0.1–0.55） | 沒有 Qwen 數據、沒有 kernel、需要雲端 QAT；在 3–4 GB 預算下品質輸給 2-bit QAT 與三值 |

### 11.3 其他修訂
1. **P4 拆成兩段**：壓縮階段用模型自己生成的資料校準（AYOT）；能力提升階段才用更強的老師蒸餾（BitDistill / ReST-EM）。
2. **新增「專精模型 + 路由」架構選項**：例如摘要用 BitDistill 三值、程式/數學用 ScaleQ 三值，每個約 1 GB；路由用 RouteLLM 式路由器，訓練資料來自我們自己的軌跡。不同專精模型可以放在不同裝置上**同時執行**，這也是「組合所有硬體」的一種實現。
3. **V0 驗證器依任務分工**：程式 → 單元測試；工具呼叫 → schema 驗證 + ToolRM 式獎勵模型（可照論文配方用開源模型自行訓練中文版）；摘要與 RAG 問答 → 上下文蘊含驗證（AutoMix）；閉卷知識題 → 不做自我驗證，改為 RAG 或轉交。
4. **R3 加入 Dovetail 拓撲**：target 超過 VRAM 預算時，用 `-ngl 0 -devd CUDA0 -ngld 99` 讓 draft 在 GPU、target 在 CPU，由 calibrator 決定是否比單純分層卸載更快。
5. **V1 技能庫**採 AWM 的離線模式 + placeholder 抽象化。
